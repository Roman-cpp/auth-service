# Composition Root: `internal/app/`

Пакет `internal/app` — единственное место в проекте, где собирается весь граф
зависимостей. Здесь конкретные реализации (Postgres, Redis, биржевые адаптеры)
подставляются в интерфейсы, объявленные у потребителей. Ни один другой пакет
не знает о полной картине — только app.

```
internal/app/
├── app.go        # структура App, точка сборки New()
├── infra.go      # инфраструктурный слой
├── storage.go    # репозитории и кэши
├── services.go   # бизнес-сервисы
└── run.go        # запуск, graceful shutdown
```

---

## Слои сборки

Файлы соответствуют слоям графа. Сборка идёт строго снизу вверх,
каждый слой зависит только от предыдущих:

```
config, logger          (слой 0 — ни от чего не зависит)
      │
      ▼
infra.go                (слой 1 — соединения и клиенты)
      │
      ▼
storage.go              (слой 2 — репозитории и кэши поверх infra)
      │
      ▼
services.go             (слой 3 — бизнес-логика поверх storage и infra)
      │
      ▼
transport (в app.go)    (слой 4 — HTTP/gRPC поверх сервисов)
```

Если новый компонент невозможно вписать в этот порядок — в дизайне есть
циклическая зависимость, и её нужно разрывать (интерфейсом у потребителя
или событиями), а не обходить.

---

## `app.go` — вершина пакета

**Что содержит:**

- Структуру `App` — контейнер собранного приложения: сервисы, транспорт,
  ссылку на инфраструктуру (для закрытия).
- Функцию `New(ctx, cfg) (*App, error)` — публичную точку входа,
  вызывающую сборку по слоям: `newInfra → newStorage → newServices`,
  затем создание транспорта.

**Зависит от:** всех остальных файлов пакета; пакетов `transport/*`.

**Правила:**

- `New` не содержит логики — только порядок сборки и обработку ошибок.
- При ошибке на любом шаге уже созданные ресурсы закрываются
  (`inf.Close()` перед `return nil, err`).
- Наружу (в `cmd/`) торчат только `App`, `New` и `Run`.

---

## `infra.go` — инфраструктурный слой

**Что содержит:**

- Приватную структуру `infra`: пул Postgres, клиент Redis, соединение NATS,
  реестр метрик, tracer, generic WebSocket-клиенты бирж.
- `newInfra(ctx, cfg, log)` — открытие всех соединений.
- `(*infra).Close()` — закрытие в обратном порядке.

**Зависит от:** конфига, логгера, пакетов `platform/*`
(database, cache, wsclient, metrics, tracing).

**Правила:**

- Ничего доменного: ни одного импорта из `internal/domain`, `internal/order`
  и т.п. Только «сырые» соединения и клиенты.
- Каждый компонент фейлится с обёрнутой ошибкой (`fmt.Errorf("postgres: %w", err)`),
  чтобы по логу старта было ясно, что именно не поднялось.

---

## `storage.go` — репозитории и кэши

**Что содержит:**

- Приватную структуру `storage` с полями-**интерфейсами**
  (`order.Repo`, `position.Repo`, ...) — типы объявлены в доменных пакетах.
- `newStorage(inf *infra)` — создание конкретных реализаций
  (`postgres.NewOrderRepo(inf.db)`) и оборачивание их кэшами-декораторами.

**Зависит от:** `infra`; пакетов реализаций (`postgres`, `*cache`, `bookstore`).

**Правила:**

- Поля структуры — интерфейсы, а не конкретные типы. Сервисы дальше
  получают `order.Repo` и не знают, Postgres за ним или Postgres + Redis.
- Кэш — декоратор с тем же интерфейсом:

  ```go
  var orders order.Repo = postgres.NewOrderRepo(inf.db)
  orders = ordercache.Wrap(orders, inf.redis, 2*time.Second)
  ```

  Замена стратегии кэширования — правка одной строки здесь,
  без изменений в сервисах.

---

## `services.go` — бизнес-сервисы

**Что содержит:**

- Приватную структуру `services` со всеми сервисами.
- `newServices(ctx, cfg, inf, st, log)` — сборку сервисов
  в топологическом порядке их зависимостей.
- Подписки на события (NATS) — обратные связи между сервисами.

**Зависит от:** `infra`, `storage`; доменных пакетов
(`order`, `risk`, `position`, `marketdata`, `strategy`); адаптеров бирж.

**Порядок сборки = граф зависимостей:**

```
marketdata ──────► risk ──────► order
     │              ▲             │
     │              │ события     │ события
     │         positions.updated  ▼ orders.filled
     └──────► strategy        position
                  │
                  └──────────► order (размещение)
```

**Правила:**

- Порядок строк в `newServices` — топологическая сортировка:
  сервис создаётся только после всех, от кого он зависит синхронно.
- Синхронные зависимости направлены строго вниз
  (order → risk → marketdata). Обратная связь — **только через события**:
  цикл `risk ↔ position ↔ order` разорван подписками NATS,
  ни один из пакетов не импортирует другой.
- Один объект может закрывать несколько интерфейсов: адаптер binance —
  это и `marketdata.Feed`, и `order.Executor`; только composition root
  знает, что за ними один тип.
- При 5+ зависимостях конструктор принимает Deps-структуру
  (`order.Deps{...}`) с именованными полями.

## `run.go` — жизненный цикл

**Что содержит:**

- `(*App).Run(ctx)` — запуск долгоживущих компонентов через `errgroup`,
  ожидание завершения, graceful shutdown.

**Правила:**

- Порядок запуска: сначала источники данных (marketdata),
  потом потребители (strategy), потом транспорт.
- Shutdown — в обратном порядке сборки:

  ```
  транспорт → доменные шаги (отмена pending-ордеров) → инфраструктура
  ```

- Shutdown ограничен таймаутом (`context.WithTimeout`), чтобы зависший
  компонент не блокировал остановку процесса.

## Матрица зависимостей файлов

| Файл          | infra | storage | services | transport | platform | домен |
|---------------|:-----:|:-------:|:--------:|:---------:|:--------:|:-----:|
| `app.go`      |   ✓   |    ✓    |    ✓     |     ✓     |          |       |
| `infra.go`    |   —   |         |          |           |    ✓     |       |
| `storage.go`  |   ✓   |    —    |          |           |          |   ✓*  |
| `services.go` |   ✓   |    ✓    |    —     |           |          |   ✓   |
| `run.go`      |   ✓   |         |    ✓     |     ✓     |          |       |

\* только интерфейсы (`order.Repo`) и пакеты реализаций (`postgres`).

Зависимости только вниз и влево — таблица нижнетреугольная.
Появление зависимости «вверх» (infra знает про сервис,
сервис знает про транспорт) — сигнал ошибки в дизайне.

## Использование из `cmd/`

```go
func main() {
	cfg, err := config.Load()
	if err != nil {
		log.Fatal(err)
	}

	ctx, stop := signal.NotifyContext(context.Background(),
		syscall.SIGINT, syscall.SIGTERM)
	defer stop()

	a, err := app.New(ctx, cfg)
	if err != nil {
		log.Fatal(err)
	}
	if err := a.Run(ctx); err != nil {
		log.Fatal(err)
	}
}
```

Для второго бинарника (например, `cmd/collector`) добавляется
`app.NewCollector(cfg)`, собирающий подмножество графа —
`newInfra` и `newStorage` переиспользуются без дублирования.

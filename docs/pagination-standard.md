# Стандарт пагинации и сортировки списковых эндпоинтов

Версия: 1.0
Применяется ко всем эндпоинтам, возвращающим коллекции (`GET /api/<resource>`).

## 1. Принципы

- Используется **offset-пагинация с общим количеством записей** (`total_items`). Это позволяет строить список страниц и переходить сразу на последнюю.
- Сортировка возможна по любому столбцу из **белого списка**, объявленного для ресурса. Произвольные имена столбцов не принимаются.
- Все параметры опциональны и имеют значения по умолчанию.
- Ответ всегда имеет одинаковую структуру: `data`, `pagination`.

## 2. Параметры запроса

| Параметр   | Тип    | По умолчанию | Ограничения                              | Описание                                  |
|------------|--------|--------------|------------------------------------------|-------------------------------------------|
| `page`     | int    | `1`          | `>= 1`                                   | Номер страницы (нумерация с единицы)      |
| `per_page` | int    | `20`         | `1..100`                                 | Количество элементов на странице          |
| `sort`     | string | `id`         | до 3 полей, только из белого списка      | Поля сортировки через запятую             |

### 2.1. Формат `sort`

```
sort=<field>[,<field>...]
```

- Поля перечисляются через запятую в порядке приоритета.
- Префикс `-` означает сортировку по убыванию; без префикса — по возрастанию.
- Одно и то же поле не может встречаться дважды.
- Сервер **всегда** добавляет `id ASC` последним полем (tiebreaker), если клиент не указал `id` сам. Это гарантирует стабильный порядок между страницами.

Примеры:

```
sort=name                  → ORDER BY name ASC, id ASC
sort=-created_at           → ORDER BY created_at DESC, id ASC
sort=-created_at,name      → ORDER BY created_at DESC, name ASC, id ASC
sort=status,-updated_at,id → ORDER BY status ASC, updated_at DESC, id ASC
```

### 2.2. Пример запроса

```
GET /api/users?page=3&per_page=25&sort=-created_at,name
```

## 3. Формат ответа

```json
{
  "data": [ ... ],
  "pagination": {
    "page": 3,
    "per_page": 25,
    "total_items": 1287,
    "total_pages": 52,
    "sort": "-created_at,name,id"
  }
}
```

### 3.1. `pagination`

| Поле          | Описание                                                                 |
|---------------|--------------------------------------------------------------------------|
| `page`        | Текущая страница                                                         |
| `per_page`    | Фактически применённый размер страницы (после ограничения максимумом)    |
| `total_items` | Общее число записей с учётом фильтров                                    |
| `total_pages` | `ceil(total_items / per_page)`; `0`, если записей нет                    |
| `sort`        | Нормализованная строка сортировки, включая добавленный сервером `id`     |

### 3.2. Навигация на клиенте

Сервер не возвращает ссылки на соседние страницы. Клиент строит всю навигацию из `pagination`:

- список номеров страниц (`1 … 45 46 47 … 52`) — из `page` и `total_pages`;
- «первая» — `page=1`, «последняя» — `page=total_pages`;
- «назад»/«вперёд» — `page ± 1` в пределах `1..total_pages`;
- при смене `sort` или `per_page` клиент сбрасывает `page` на `1`;
- если после обновления `page > total_pages`, клиент переходит на `total_pages`.

Блок `links` (`self`/`first`/`prev`/`next`/`last`) в стандарт не входит. Он может быть добавлен как неломающее расширение, если появятся внешние потребители API или потребуется `useInfiniteQuery`-подобный обход по `next`.

## 4. Обработка ошибок и граничных случаев

| Ситуация                                    | Поведение сервера                                              |
|---------------------------------------------|----------------------------------------------------------------|
| `page < 1` или не число                     | Используется значение по умолчанию (`1`)                       |
| `per_page` вне диапазона                    | Значение приводится к границе (`1` или `100`)                  |
| `page > total_pages`                        | `200 OK`, `data: []`, `pagination` заполнен корректно                |
| Поле в `sort` не входит в белый список      | `400 Bad Request`, `{"error": "invalid sort field: <name>"}`   |
| Дубликат поля в `sort`                      | `400 Bad Request`, `{"error": "duplicate sort field: <name>"}` |
| Более 3 полей в `sort`                      | `400 Bad Request`, `{"error": "too many sort fields"}`         |

## 5. Требования к реализации

1. **Белый список столбцов** объявляется для каждого ресурса как отображение «имя в API → имя столбца в БД». Имя из запроса никогда не подставляется в SQL напрямую.
2. Запрос выполняется как `SELECT ... ORDER BY <cols> LIMIT :per_page OFFSET :(page-1)*per_page`.
3. `total_items` считается отдельным `COUNT(*)` с теми же условиями фильтрации.
4. Для nullable-столбцов в `ORDER BY` явно указывается `NULLS LAST`.
5. Составные индексы создаются под наиболее частые комбинации сортировок; комбинации, не покрытые индексами, допустимы, но ограничены лимитами на `per_page` и число полей.
6. При росте таблицы, когда `COUNT(*)` становится узким местом, допускается кеширование `total_items` с коротким TTL. Переход на keyset-пагинацию для такого ресурса означает отказ от `total_pages` и `last` и оформляется отдельным решением.

```go
    "status":     "status",

    "updated_at": "updated_at",
}
```

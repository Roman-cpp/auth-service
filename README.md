# auth-service

Сервис аутентификации на Go. Построен по принципам DDD.

## Требования

- [Docker](https://docs.docker.com/get-docker/) + Docker Compose
- [Go 1.24+](https://go.dev/dl/) (только для локального запуска без Docker)

## Быстрый старт

### 1. Настройка переменных окружения

```bash
cp .env.example .env
```

Обязательно задайте `JWT_SECRET` — сервис не запустится без него:

```bash
# Генерация надёжного секрета
openssl rand -hex 32
```

Основные переменные `.env`:

| Переменная       | По умолчанию                                    | Описание               |
|------------------|-------------------------------------------------|------------------------|
| `SERVICE_NAME`   | `auth-service`                                  | Имя сервиса            |
| `SERVICE_ENV`    | `local`                                         | Окружение              |
| `SERVICE_PORT`   | `8080`                                          | Порт внутри контейнера |
| `DB_HOST`        | `postgres`                                      | Хост БД                |
| `DB_PORT`        | `5432`                                          | Порт БД                |
| `DB_USER`        | `postgres`                                      | Пользователь БД        |
| `DB_PASSWORD`    | `postgres`                                      | Пароль БД              |
| `DB_NAME`        | `auth-db`                                       | Имя базы данных        |
| `JWT_SECRET`     | —                                               | **Обязателен**, не короче 32 символов |
| `JWT_ACCESS_TTL` | `15m`                                           | TTL access-токена      |
| `JWT_REFRESH_TTL`| `168h`                                          | TTL refresh-токена     |
| `JWT_MFA_TTL`    | `10m`                                           | TTL токена второго шага входа |

### Одноразовые коды

| Переменная                  | По умолчанию | Описание                                  |
|-----------------------------|--------------|-------------------------------------------|
| `AUTH_CODE_TTL`             | `10m`        | Сколько живёт код из письма                |
| `AUTH_CODE_RESEND_COOLDOWN` | `60s`        | Минимальный интервал между письмами        |
| `AUTH_CODE_MAX_ATTEMPTS`    | `5`          | Неверных попыток ввода до блокировки кода  |

### Удаление аккаунта

| Переменная               | По умолчанию | Описание                                   |
|--------------------------|--------------|--------------------------------------------|
| `ACCOUNT_RESTORE_WINDOW` | `8760h` (год)| Сколько удалённый аккаунт можно восстановить |

### Роли

| Переменная         | По умолчанию | Описание                                                        |
|--------------------|--------------|-----------------------------------------------------------------|
| `MODERATOR_EMAILS` | — (пусто)    | Адреса через запятую: при старте получают роль модератора       |

Так появляется первый модератор — назначить его больше некому. Удаление адреса
из списка роль **не** снимает; снять её сейчас можно только в базе
(`UPDATE users SET role = 'user' WHERE email = ...`).

### SMTP

| Переменная       | По умолчанию          | Описание                                        |
|------------------|-----------------------|-------------------------------------------------|
| `SMTP_HOST`      | — (пусто)             | Пустой хост = коды пишутся в лог вместо отправки |
| `SMTP_PORT`      | `587`                 | Порт SMTP                                        |
| `SMTP_TRANSPORT` | `starttls`            | `none` \| `starttls` \| `tls`                     |
| `SMTP_USERNAME`  | — (пусто)             | Пустой логин = подключение без аутентификации    |
| `SMTP_PASSWORD`  | — (пусто)             | Пароль SMTP                                      |
| `SMTP_FROM`      | `no-reply@nexus.local`| Адрес отправителя                                |
| `SMTP_FROM_NAME` | `Nexus`               | Имя отправителя                                  |
| `SMTP_TIMEOUT`   | `5s`                  | Таймаут на отправку одного письма                |

Конфиг проверяется на старте: слишком короткий `JWT_SECRET`, неизвестный
`SMTP_TRANSPORT`, кулдаун длиннее TTL кода и `JWT_MFA_TTL` короче
`AUTH_CODE_TTL` не дадут сервису подняться.

### Почта в dev

В `docker-compose-dev.yml` поднимается **mailpit**: он принимает SMTP на 1025
и никуда письма не пересылает. Коды подтверждения читаются в веб-интерфейсе
на <http://localhost:8025>. Реальные ящики при разработке не задеваются.

Без docker compose (`go run ./cmd/auth-service`) `SMTP_HOST` можно оставить
пустым — коды будут писаться в лог.

### 2. Запуск

```bash
docker compose up --build
```

Сервис будет доступен на `http://localhost:8085`.

Для dev-окружения:

```bash
docker compose -f docker-compose-dev.yml up --build
```

### 3. Миграции

Миграции применяются автоматически при первом запуске через `docker-entrypoint-initdb.d`.

Для ручного управления миграциями:

```bash
# Применить все
go run ./cmd/migrate up

# Откатить последнюю
go run ./cmd/migrate down

# Текущая версия
go run ./cmd/migrate version
```

DSN подтягивается из `.env` автоматически. Можно переопределить флагом:

```bash
go run ./cmd/migrate -dsn "pgx5://user:pass@host:5432/db" up
```

## Локальный запуск без Docker

```bash

go run ./cmd/auth-service
```

## Аутентификация

Регистрация и вход двухфакторные: пароль плюс одноразовый код из письма.

### Регистрация

```
POST /api/v1/auth/register      → 201, код уходит на почту, сессии НЕТ
POST /api/v1/auth/verify-email  → 200 + куки сессии
POST /api/v1/auth/resend-code   → 202
```

Пока адрес не подтверждён, `POST /auth/login` отвечает `403 email_not_verified`.
Повторная регистрация на **неподтверждённый** адрес перезаписывает заявку —
иначе чужой email можно было бы занять навсегда, просто начав регистрацию.
Подтверждённый аккаунт защищён: `409 email_taken`.

### Вход

```
POST /api/v1/auth/login       → 200 {"mfa_required": false} + куки сессии
                              → 200 {"mfa_required": true}  + кука mfa_token
POST /api/v1/auth/mfa/verify  → 200 + куки сессии
POST /api/v1/auth/mfa/resend  → 202
```

Второй шаг нужен, только если у аккаунта включён второй фактор.

### Управление вторым фактором (требуется сессия)

```
POST /api/v1/auth/2fa/enable   {"password"} → 202, код на почту
POST /api/v1/auth/2fa/confirm  {"code"}     → 200, фактор включён
POST /api/v1/auth/2fa/disable  {"password"} → 200, фактор выключен
```

### Сброс и смена пароля

```
POST /api/v1/auth/password/forgot  {"email"}                           → 202, код на почту
POST /api/v1/auth/password/reset   {"email","code","password"}         → 200, все сессии отозваны
POST /api/v1/auth/password/change  {"current_password","new_password"} → 200 + новые куки сессии
```

`forgot` отвечает одинаково для любого адреса и не сообщает, зарегистрирован
ли он. На **неподтверждённый** адрес письмо не уходит: менять там нечего,
такую заявку перезаписывает повторная регистрация.

`reset` сессию **не** открывает, хотя код предъявлен, — в отличие от
`verify-email`. Код сброса приходит на ту же почту, что и код второго фактора:
выдай сброс сессию, доступ к ящику отменял бы 2FA целиком. После смены пароля
нужно войти обычным путём, со всеми факторами.

`change` требует сессию **и** текущий пароль: одной перехваченной сессии для
смены пароля недостаточно.

Обе операции отзывают **все** refresh-токены пользователя — пароль меняют в том
числе после утечки. `change` сразу выдаёт вызывающему клиенту новую пару, так
что разлогиниваются только остальные устройства. Ранее выданные access-токены
отзываются сразу же (см. «Отзыв access-токенов»).

Новый пароль, совпадающий с текущим, отвергается — `password_unchanged`.

### Роли и админка

Ролей две: `user` и `moderator`. Роль лежит в access-токене, отдаётся в
`/auth/me` (поле `role`) и заголовком `X-User-Roles` из `/auth/validate` —
его gateway пробрасывает остальным сервисам.

```
GET  /api/v1/admin/users?q=&limit=50&offset=0 → 200 {"users": [...], "total": N}
POST /api/v1/admin/users {"email","last_name","first_name","patronymic"?,"role"?}
                                              → 201 {"user": ..., "temporary_password": "..."}
```

Обе ручки — только для модератора: без сессии `401`, без роли `403 forbidden`.
Роль берётся из токена, но устареть не может: её смена отзывает все выданные
токены пользователя (см. «Отзыв access-токенов»).

Заведённый модератором аккаунт сразу считается подтверждённым (адрес ввёл
модератор), а пароль у него **временный**: его генерирует сервис и отдаёт
только в ответе на `POST`. Неподтверждённая заявка на тот же адрес
перезаписывается, подтверждённый аккаунт — нет (`409 email_taken`).

### Временный пароль

```
POST /api/v1/auth/login            {"email","password"}                 → 403 password_change_required
POST /api/v1/auth/password/initial {"email","password","new_password"} → как у /auth/login
```

Вход с временным паролем сессию **не** открывает: пароль видел модератор, и
секретом владельца он не является. Ошибка `password_change_required` приходит
только при верном пароле, иначе — обычный `invalid_credentials`. `initial`
меняет пароль и сразу продолжает вход: сессия или, если включён, второй фактор.
Повторно он не срабатывает — `409 password_not_temporary`.

### Удаление и восстановление аккаунта

```
DELETE /api/v1/users/{id}             → 200 {"restore_available_until": ...}
POST   /api/v1/auth/account/restore   {"email","password"} → 200 {"user": ...}
```

Удаление логическое: строка помечается `deleted_at` и живёт, пока аккаунт
можно вернуть (`ACCOUNT_RESTORE_WINDOW`, по умолчанию год). По истечении окна
её физически сносит уборщик — вместе с кодами и refresh-токенами по каскаду.

**Адрес освобождается сразу.** Уникальность email считается только среди живых
аккаунтов (частичный индекс `idx_users_email_active`), поэтому на него можно
зарегистрироваться заново хоть на следующей минуте. До этого момента старый
аккаунт восстановим; как только адрес занял новый **подтверждённый** владелец —
восстановление отвечает `409 email_taken`. Незавершённая чужая регистрация
восстановлению не мешает: она сносится, потому что ничего не доказывает, а
восстанавливающий предъявил пароль.

Восстановление сессию не открывает — после возврата аккаунта нужно войти
обычным путём, со вторым фактором, если он был включён. Поэтому пароля для
восстановления достаточно: прав сверх тех, что даёт обычный вход, оно не даёт.

Вход по удалённому аккаунту с **верным** паролем отвечает `403 account_deleted`
— иначе про возможность восстановления владелец не узнает. При неверном пароле
и после окончания окна ответ неотличим от «неверный email или пароль»: адрес,
который когда-то был зарегистрирован, наружу не подсвечивается.

### Токены

Access- и MFA-токен подписаны одним секретом и различаются claim `typ`
(`access` / `mfa`). Без этой проверки токен первого шага проходил бы как
полноценный access — то есть второй фактор обходился бы предъявлением
токена, выданного до ввода кода.

MFA-токен stateless и не отзывается: от повторного использования защищает
сам код — он гасится в БД при успешной проверке. Но он несёт версию токенов
пользователя, и после смены пароля первый шаг входа приходится пройти заново.

Содержимое access-токена:

```json
{"typ": "access", "role": "user", "ver": 3, "sub": "<id>", "iat": ..., "exp": ...}
```

Почты и других персональных данных в токене нет: payload подписан, но не
зашифрован. Токен принимается **только** из httpOnly-куки `access_token`,
заголовок `Authorization` не читается.

### Проверка токена гейтвеем

```
GET /api/v1/auth/validate → 204 + X-User-Id, X-User-Roles
```

В него ходит `auth_request` gateway на каждый запрос к защищённым сервисам,
поэтому он не читает базу и не отдаёт тела: подпись, срок и отзыв — всё
проверяется в памяти. `/auth/me` остаётся для фронтенда — ему нужен профиль.

### Отзыв access-токенов

У пользователя есть счётчик `token_version`. Триггер в базе поднимает его при
смене роли, пароля и удалении аккаунта — в том числе при ручном `UPDATE` из
консоли — и записывает новую версию в `token_revocations`. Access-токен несёт
версию, с которой выдан (`ver`); токен с версией ниже текущей отвергается
с `401`, после чего клиент молча делает refresh и получает токен с актуальной
ролью (или отказ, если аккаунта больше нет).

Сервис держит копию `token_revocations` в памяти:

* изменения этого экземпляра действуют сразу;
* изменения из консоли и с других экземпляров — не позже чем через 5 секунд
  (фоновая синхронизация);
* если список не удаётся обновить дольше минуты, токены не принимаются вовсе
  (`503`): пропущенный отзыв хуже недоступности;
* без загруженного списка сервис не стартует.

Записи старше двух `JWT_ACCESS_TTL` убирает уборщик: токенов со старыми
версиями к этому моменту уже нет.

### Ограничения на коды

* один живой код на пару (пользователь, назначение) — гарантируется
  уникальным частичным индексом в `auth_codes`;
* хранится bcrypt-хеш, а не SHA-256: в коде всего 6 цифр, быстрый хеш при
  утечке таблицы перебирается мгновенно;
* повторный запрос внутри `AUTH_CODE_RESEND_COOLDOWN` не шлёт второе письмо,
  а возвращает сроки уже действующего кода;
* после `AUTH_CODE_MAX_ATTEMPTS` неверных вводов код перестаёт приниматься
  даже при верном значении — нужен новый.

## Структура проекта

```
cmd/
  auth-service/   — точка входа сервиса
  migrate/        — CLI для управления миграциями
internal/
  config/         — загрузка конфигурации из env
  domain/         — бизнес-логика (DDD-агрегаты)
  handler/        — HTTP-обработчики
  mailer/         — отправка писем (SMTP + шаблоны)
  middleware/     — JWT и прочие middleware
  repository/     — реализации репозиториев (PostgreSQL)
  router/         — маршрутизация
  service/        — токены, одноразовые коды, сценарии входа
migrations/       — SQL-миграции
docs/             — документация по доменной модели
```

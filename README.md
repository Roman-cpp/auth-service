# auth-service

Сервис аутентификации на Go. Построен по принципам DDD.

## Требования

- [Docker](https://docs.docker.com/get-docker/) + Docker Compose
- [Go 1.24+](https://go.dev/dl/) (только для локального запуска без Docker)

## Быстрый старт

### 1. Настройка переменных окружения

```bash
cp .env.example .env
```

Обязательно задайте `JWT_SECRET` — сервис не запустится без него:

```bash
# Генерация надёжного секрета
openssl rand -hex 32
```

Основные переменные `.env`:

| Переменная       | По умолчанию                                    | Описание               |
|------------------|-------------------------------------------------|------------------------|
| `SERVICE_NAME`   | `auth-service`                                  | Имя сервиса            |
| `SERVICE_ENV`    | `local`                                         | Окружение              |
| `SERVICE_PORT`   | `8080`                                          | Порт внутри контейнера |
| `DB_HOST`        | `postgres`                                      | Хост БД                |
| `DB_PORT`        | `5432`                                          | Порт БД                |
| `DB_USER`        | `postgres`                                      | Пользователь БД        |
| `DB_PASSWORD`    | `postgres`                                      | Пароль БД              |
| `DB_NAME`        | `auth-db`                                       | Имя базы данных        |
| `JWT_SECRET`     | —                                               | **Обязателен**, не короче 32 символов |
| `JWT_ACCESS_TTL` | `15m`                                           | TTL access-токена      |
| `JWT_REFRESH_TTL`| `168h`                                          | TTL refresh-токена     |
| `JWT_MFA_TTL`    | `10m`                                           | TTL токена второго шага входа |

### Одноразовые коды

| Переменная                  | По умолчанию | Описание                                  |
|-----------------------------|--------------|-------------------------------------------|
| `AUTH_CODE_TTL`             | `10m`        | Сколько живёт код из письма                |
| `AUTH_CODE_RESEND_COOLDOWN` | `60s`        | Минимальный интервал между письмами        |
| `AUTH_CODE_MAX_ATTEMPTS`    | `5`          | Неверных попыток ввода до блокировки кода  |

### SMTP

| Переменная       | По умолчанию          | Описание                                        |
|------------------|-----------------------|-------------------------------------------------|
| `SMTP_HOST`      | — (пусто)             | Пустой хост = коды пишутся в лог вместо отправки |
| `SMTP_PORT`      | `587`                 | Порт SMTP                                        |
| `SMTP_TRANSPORT` | `starttls`            | `none` \| `starttls` \| `tls`                     |
| `SMTP_USERNAME`  | — (пусто)             | Пустой логин = подключение без аутентификации    |
| `SMTP_PASSWORD`  | — (пусто)             | Пароль SMTP                                      |
| `SMTP_FROM`      | `no-reply@nexus.local`| Адрес отправителя                                |
| `SMTP_FROM_NAME` | `Nexus`               | Имя отправителя                                  |
| `SMTP_TIMEOUT`   | `5s`                  | Таймаут на отправку одного письма                |

Конфиг проверяется на старте: слишком короткий `JWT_SECRET`, неизвестный
`SMTP_TRANSPORT`, кулдаун длиннее TTL кода и `JWT_MFA_TTL` короче
`AUTH_CODE_TTL` не дадут сервису подняться.

### Почта в dev

В `docker-compose-dev.yml` поднимается **mailpit**: он принимает SMTP на 1025
и никуда письма не пересылает. Коды подтверждения читаются в веб-интерфейсе
на <http://localhost:8025>. Реальные ящики при разработке не задеваются.

Без docker compose (`go run ./cmd/auth-service`) `SMTP_HOST` можно оставить
пустым — коды будут писаться в лог.

### 2. Запуск

```bash
docker compose up --build
```

Сервис будет доступен на `http://localhost:8085`.

Для dev-окружения:

```bash
docker compose -f docker-compose-dev.yml up --build
```

### 3. Миграции

Миграции применяются автоматически при первом запуске через `docker-entrypoint-initdb.d`.

Для ручного управления миграциями:

```bash
# Применить все
go run ./cmd/migrate up

# Откатить последнюю
go run ./cmd/migrate down

# Текущая версия
go run ./cmd/migrate version
```

DSN подтягивается из `.env` автоматически. Можно переопределить флагом:

```bash
go run ./cmd/migrate -dsn "pgx5://user:pass@host:5432/db" up
```

## Локальный запуск без Docker

```bash
# Запустить только БД
docker compose up postgres -d

# Запустить сервис
go run ./cmd/auth-service
```

## Аутентификация

Регистрация и вход двухфакторные: пароль плюс одноразовый код из письма.

### Регистрация

```
POST /api/v1/auth/register      → 201, код уходит на почту, сессии НЕТ
POST /api/v1/auth/verify-email  → 200 + куки сессии
POST /api/v1/auth/resend-code   → 202
```

Пока адрес не подтверждён, `POST /auth/login` отвечает `403 email_not_verified`.
Повторная регистрация на **неподтверждённый** адрес перезаписывает заявку —
иначе чужой email можно было бы занять навсегда, просто начав регистрацию.
Подтверждённый аккаунт защищён: `409 email_taken`.

### Вход

```
POST /api/v1/auth/login       → 200 {"mfa_required": false} + куки сессии
                              → 200 {"mfa_required": true}  + кука mfa_token
POST /api/v1/auth/mfa/verify  → 200 + куки сессии
POST /api/v1/auth/mfa/resend  → 202
```

Второй шаг нужен, только если у аккаунта включён второй фактор.

### Управление вторым фактором (требуется сессия)

```
POST /api/v1/auth/2fa/enable   {"password"} → 202, код на почту
POST /api/v1/auth/2fa/confirm  {"code"}     → 200, фактор включён
POST /api/v1/auth/2fa/disable  {"password"} → 200, фактор выключен
```

### Токены

Access- и MFA-токен подписаны одним секретом и различаются claim `typ`
(`access` / `mfa`). Без этой проверки токен первого шага проходил бы как
полноценный access — то есть второй фактор обходился бы предъявлением
токена, выданного до ввода кода.

MFA-токен stateless и не отзывается: от повторного использования защищает
сам код — он гасится в БД при успешной проверке.

### Ограничения на коды

* один живой код на пару (пользователь, назначение) — гарантируется
  уникальным частичным индексом в `auth_codes`;
* хранится bcrypt-хеш, а не SHA-256: в коде всего 6 цифр, быстрый хеш при
  утечке таблицы перебирается мгновенно;
* повторный запрос внутри `AUTH_CODE_RESEND_COOLDOWN` не шлёт второе письмо,
  а возвращает сроки уже действующего кода;
* после `AUTH_CODE_MAX_ATTEMPTS` неверных вводов код перестаёт приниматься
  даже при верном значении — нужен новый.

## Структура проекта

```
cmd/
  auth-service/   — точка входа сервиса
  migrate/        — CLI для управления миграциями
internal/
  config/         — загрузка конфигурации из env
  domain/         — бизнес-логика (DDD-агрегаты)
  handler/        — HTTP-обработчики
  mailer/         — отправка писем (SMTP + шаблоны)
  middleware/     — JWT и прочие middleware
  repository/     — реализации репозиториев (PostgreSQL)
  router/         — маршрутизация
  service/        — токены, одноразовые коды, сценарии входа
migrations/       — SQL-миграции
docs/             — документация по доменной модели
```
